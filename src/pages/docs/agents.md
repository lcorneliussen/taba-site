## Agent skills in v0.2.4

With [v0.2.4](https://github.com/lcorneliussen/taba/releases/tag/v0.2.4), rendered skills use `taba-*`: start with `/taba-start`. Old `wtc-*` names remain compatibility shims during 0.2.x. A harness override under its old name still wins; rename its folder and `name:` together when migrating. Section patches and their base digests move with the override; review reported base drift before accepting it.

`taba open` starts `taba status --tui` and `taba browse` for collections pinned at 0.2.0 or later; older pins retain the `wtc` commands. The earlier examples below keep their historical baseline. See the [published conventions](https://github.com/lcorneliussen/taba/blob/v0.2.4/docs/conventions.md) for migration order.

## Start at the collection

Open your agent or editor in the collection folder, not in an unrelated checkout. That puts the repositories involved in the task in one workspace.

WTC supplies standard collection guidance. A project-owned harness adds repository registration, project policy, configuration, and hooks. Your application repositories keep their normal development commands.

## Orient before editing

Check `wtc status` to confirm the active collection and worktrees. The `/wtc-start` procedure is the agent orientation entry point where that skill is installed.

Ask the agent to identify the repositories the change touches, then work in those collection worktrees. Add another repository if the task grows.

For example:

> Work on the sign-in error in this collection. Check the API response and frontend handling, make the change in both repositories if needed, and run their relevant checks.

## Keep the project in charge

Use ordinary build and test commands. WTC organizes the workspace; it does not dictate a framework, replace tests, or decide when code is ready to merge.

An ordinary editor and terminal work too. Agent use is optional. `wtc open` is another interface for a herdr workspace with agent, browse, shell, and status panes when those tools are installed.

## Agents under OpenClaw

OpenClaw has a distinct managed workflow. One conversation can drive several repositories, while hidden owner sessions hold the worktrees. Worktree creation and publication follow tool plans generated by WTC.

Read [Under OpenClaw](../openclaw/) before creating or publishing worktrees on a gateway.
